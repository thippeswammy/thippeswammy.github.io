# 1. The VRAM Fix: "The Two-Phase Execution" (Zero OOM Guarantee)
Instead of trying to suspend and resume nodes dynamically (which is prone to crashing PyTorch's CUDA allocator on a 4GB RTX 3050), we physically separate the AI models into two sequential phases.

Phase A (Perception & TKG): You run your rosbag playback. YOLOv8, SegFormer, MiDaS, and the TKG all run normally. However, instead of triggering the vlm_async_node mid-run, the TKG simply writes a "VLM Request Ticket" (containing the cropped image path, coordinates, and prompt) to a JSON queue on your hard drive.

Phase B (VLM Audit): The rosbag finishes. You kill the ROS perception nodes, completely freeing up the GPU. Then you spin up a dedicated VLM batch script. It loads Qwen-VL-2B (taking up its 1.5GB comfortably), churns through the JSON queue of tickets, and updates the TKG states before generating the final Folium map.

The Result: You never have your perception models and your VLM in VRAM at the same time. Zero memory fragmentation. Zero OOM errors.

# 2. The GPS Fix: "Look-Ahead Anchoring"
Because you are offline, you have the superpower of seeing the future. We don't have to guess if the first GPS coordinate is accurate.

The Idea: Before launching your main infratrack_offline.launch.py, you run a tiny Python pre-flight script. This script rapidly reads only the /fix topic from the rosbag. It looks for the first 10-second window where the GPS covariance (uncertainty) drops to its absolute lowest and satellite lock is stable.

The Execution: It extracts that highly accurate coordinate, saves it as the world -> map ENU anchor, and then kicks off the main launch file. This guarantees your expected OSM layer perfectly aligns with the real world right out of the gate.

# 3. The Ghost Sign Fix: "The TKG Funnel"
Even if we batch the VLM at the end, we don't want it spending an hour analyzing every single political poster and shop sign in Bengaluru.

The Idea: Strengthen the TKG's internal logic before it creates a VLM ticket. If an entity is marked as a GHOST candidate, it must pass a dual-filter:

Spatial Filter: Is the bounding box physically within the road_ok or sidewalk mask generated by SegFormer? If it's floating 20 meters off the road, discard it.

OCR Filter: Does EasyOCR detect recognizable text? If it just sees gibberish or a blank rectangle, discard it before bothering the VLM.

# 5. Building the Universal Rosbag (Synchronizing the Data)
Your ROS 2 system doesn't know how to read folders full of CSVs and MP4s. It expects a continuous stream of synchronized messages. You will write a Python script using the rosbags library to merge everything into a single .db3 file.

# 6.  Building the Rosbag: "True-Time Sequential Packing"
Instead of forcing the IMU and GPS to match the camera frames, your Python script will act like a timeline scheduler.

The Logic: You extract the UNIX timestamps from every row of the Location.csv (e.g., 10 Hz), the Accelerometer.csv (e.g., 100 Hz), and every frame of the Video (e.g., 30 Hz).

The Merge: You put all of these data points into one giant list and sort it chronologically.

The Export: Your script writes them into the rosbag2 file in that exact chronological order. The rosbag doesn't care that the frequencies are different; it just stores the data exactly as it happened in the real world.

# 7. The ROS 2 Magic: The TF2 "Time Machine"
Once that data is in the rosbag, ROS 2 is specifically designed to handle this exact multi-frequency scenario perfectly. Here is how your architecture manages the compute:

The High-Hz Background Engine: Your ekf_node will subscribe to /imu/data and /fix. It will spin constantly at 100Hz, fusing that data to build an incredibly smooth, continuous trajectory (the odom frame). It requires almost zero compute power.

The Heavy Camera Compute: Your YOLO, SegFormer, and TKG nodes only wake up when an /camera/image_raw message arrives (e.g., at 30Hz, or slower during offline playback).

The Connection (Interpolation): When your heavy perception pipeline needs to know exactly where the camera was in 3D space to project a stop sign, it asks the tf_buffer for the coordinate at the exact timestamp of that specific image. ROS 2 looks at the high-frequency IMU/GPS data bounding that exact millisecond and mathematically interpolates the perfect 3D position.

Summary of the Fix
You don't need to align the data yourself! You just need to accurately write the real timestamps into the .db3 file. ROS 2's TF system will handle interpolating the high-frequency tracking data to match the lower-frequency camera frames.
